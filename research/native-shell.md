# Hermes Desktop native-shell audit

Audited source: upstream `NousResearch/hermes-agent`, commit `a566d20d226a8e2ef0747639dc8a3fc1c43f9dba`, desktop package `0.17.6`. This is a source audit, not a running-app verification. Paths below are repository-relative; line numbers are from that commit. Read root and `apps/desktop/AGENTS.md`. No upstream files modified.

## Architecture conclusion

Electron is a large host application, not a disposable window around chat. `apps/desktop/electron/main.ts` has 18,685 lines; `preload.ts` has 627 lines plus topical modules. Its responsibilities include local runtime installation and supervision, many concurrent profiles/connections, machine filesystem and Git, terminals, credentials, authenticated HTTP mediation, browser isolation, auxiliary windows, updates and crash recovery. Replacing React with SwiftUI without explicitly replacing these services loses substantial functionality.

Keep Hermes Python as the agent and gateway. The desktop launches a headless backend with `hermes [--profile NAME] serve --host 127.0.0.1 --port 0` (`electron/backend-command.ts:17`, `main.ts:13071`). Native macOS should launch and speak to the same backend; neither Swift nor a mobile framework should reimplement the agent turn loop, memory, tool execution, provider setup or durable sessions. Runtime discovery, host operations and UI state need separate Swift modules with explicit ownership. iOS should consume a remote gateway and common model/protocol packages; local Python installation, process execution and macOS window controls are not portable services.

No existing Swift target, Xcode project or `Package.swift` was found in the repository. `electron/native/command-screenshot-monitor.m` is a small existing Objective-C native helper, not a native application. `apps/bootstrap-installer` is a separate Tauri installer; its presence must not be mistaken for a native desktop product.

## Local runtime, install, recovery and shutdown

1. **Discovery is a validated precedence ladder** (`main.ts:5078`): explicit developer root, unbundled source tree, canonical active runtime, existing CLI on PATH (or explicit deployment override), Python with importable Hermes, then bootstrap-needed. Existing installations are adopted without falsely taking installation ownership. PATH includes login-shell discovery, managed Node, venv and macOS Homebrew fallback (`main.ts:13181`, `backend-env.ts:112`, `shell-path.ts`). A healthy CLI install can work without the desktop bootstrap marker.
2. **First-run installation is an observable stage protocol**, not a single shell command (`bootstrap-runner.ts:883`; `scripts/install.sh:352`). Installer manifest stages: prerequisites, repository, venv, Python dependencies, Node/browser dependencies, CLI PATH, config/skills, interactive setup, gateway, complete; optional desktop build is omitted when the desktop itself bootstraps. Source downloads are pinned by install stamp where present. Native must retain progress, log tail, cancellation, repair, setup-versus-remote decision, and partial-install recovery. Do not invoke the current desktop-build stage from the Swift app.
3. **Spawn is authenticated and profile-pinned** (`main.ts:13246`): random session token, explicit home/cwd/profile, parent PID/start marker/spawn nonce and `HERMES_DESKTOP=1`. That flag enables backend desktop behavior including cron ticking; it is not the correct way to identify GUI session capabilities. Start stdout/stderr capture and port-sentinel listener before any await. Accept both `HERMES_BACKEND_READY` and historical `HERMES_DASHBOARD_READY`; probe HTTP and the actual authenticated WebSocket before calling the runtime ready (`backend-ready.ts:3`, `main.ts:13427`). Cold-start tolerant deadlines, observed child exit and log tail make failures actionable.
4. **Older runtime fallback is narrow**: `serve` unsupported means use `dashboard --no-open` only (`backend-command.ts:17`, `backend-serve-support.ts`). Do not fall back because an otherwise supported invocation transiently failed.
5. **Backend pool is real product behavior**: non-primary local profiles have a resource-constrained pool (default three children, ten-minute idle; user configurable) and foreground/background spawn priority (`pool-limits.ts:20`, `pool-spawn-coordinator.ts:149`, `main.ts:12466`). Active turns/cron and live scope ownership protect children from careless eviction; cooperative retirement parks clients before stopping a child. Port this policy, not simply a dictionary of `Process` objects.
6. **Shutdown and recovery are race-sensitive**: ownership claims prevent terminating unrelated or reused-PID processes (`backend-ownership.ts`, `main.ts:3604`); orphan sweep is limited to the single-instance lock holder; a permanent shutdown cancellation fence prevents late discoveries from spawning after quit (`local-backend-lifecycle.ts:37`). Drain backend starts, children, SSH and PTYs, but bound the wait (`main.ts:18557`). On macOS closing the final window leaves the Dock application alive; actual quit/update handoff does not (`main.ts:18675`). Active work prompts before quit (`main.ts:18515`). Unexpected exit recovery is bounded; local install failures latch for deliberate repair, transient remotes retry, real auth and host-key changes require action.

**Native recommendation:** a macOS `RuntimeSupervisor` actor owning `Process`/pipes plus an independent lifecycle state machine; helper process only if needed for crash survival or privilege isolation. No privileged helper is required merely to run a per-user Hermes backend. Preserve compatible user state under the effective Hermes home, and put native UI preferences/caches under a distinct native app container. Adopt existing CLI runtime read-only until the user initiates install/update. The new native app must never let `hermes update` replace its Swift bundle with Electron.

**Shutdown nuance verified in the backend:** OS detachment does not imply a gateway always survives Desktop. Actions use `start_new_session=True` (`hermes_cli/web_server_gateway.py:477`), but Desktop serve shutdown calls `_terminate_desktop_managed_gateway` (`hermes_cli/web_server.py:279`), which terminates the recorded `gateway-restart` child (`hermes_cli/web_server_gateway.py:282`). Distinguish independently service-managed gateways from desktop-owned processes. A reliable iOS host needs explicit service ownership; some higher-level source guides describe gateway detachment more broadly than this implementation.

## Connections, identity, OAuth and Cloud

Routes must include at least connection ID + profile, not only a profile name. The v2 registry contains local, URL remote, Cloud and SSH connections simultaneously, unique device labels, primary/last-used/launch mode, and disambiguated agent handles (`connection-registry.ts:1`). Current registry assumes exactly one local entry; iOS should not inherit that as a fake local runtime. It needs a remote-only registry variant or explicit local-host capability.

HTTP, WebSocket, notifications, windows, downloads, preview URLs and terminals must use the same route owner. Native code needs strong route and session ID types (durable session, runtime session, lineage root) shared with the UI. `handleHermesApiRequest` already contains extensive profile/connection routing plus rename/delete lifecycle compensation (`main.ts:16951`); port its decisions behind a router with contract tests instead of scattering profile query parameters among views.

`api-transport.ts:1` uses separate pools for interactive JSON and long downloads, bounded retries, and avoids retrying non-idempotent operations after an ambiguous send. A native `URLSession` adapter must preserve that property; automatically retrying prompt submit on disconnection can duplicate work.

Remote auth modes include static session token, gateway-brokered native OAuth, and older embedded cookie auth. Capability discovery uses `/api/status` `auth_flows` and `/api/auth/providers` (`native-oauth.ts:89`). Native OAuth is PKCE/S256 + random state + an ephemeral loopback listener + external system browser + token/refresh endpoints (`native-oauth-login.ts:90`). Fresh single-use WebSocket tickets are minted for each dial, with no reuse of cached OAuth ticket URLs. Network errors/429/5xx are not credential rejection; only confirmed 401/403 trigger reauthentication (`connection-config.ts:121`, `main.ts:8349`). Custom access-proxy headers remain scoped to the matching remote origin/path.

**Concrete iOS prerequisite:** `hermes_cli/dashboard_auth/routes.py:218` accepts only `http://127.0.0.1` or `http://[::1]` native redirects. An `ASWebAuthenticationSession` flow with registered universal/app callbacks requires a server-side mobile callback contract with explicit allowed destinations and PKCE/state validation. This is not a client-only port. macOS can first preserve the proven loopback flow.

Cloud discovery is another auth plane (`main.ts:8416`, `:8752`): portal persistent cookies, silent renewal, `/api/agents`, org-choice on 409, and per-agent silent sign-in. Do not assume gateway PKCE alone reproduces Cloud onboarding; validate and plan native portal support separately. Existing flows rely on browser session cookies and window-mediated renewal.

**Secrets:** `secret-storage-policy.ts:1` intentionally defaults gateway/token encryption OFF because Electron `safeStorage` could cause blocking keychain dialogs. Secrets are then stored as plain data in owner-only files; older encrypted blobs have one-time migration behavior. Native should use a first-class Keychain implementation with controlled access/error states and explicit import migration. Do not copy the plaintext default or silently delete unreadable credentials. Also do not claim Keychain is already the current default. Ciphertexts from Electron are not automatically interchangeable with a new native Keychain service identity.

## SSH and remote workspace behavior

`ssh-connection.ts:1` deliberately uses system OpenSSH for `~/.ssh/config`, agent, ProxyJump and hardware-key support. It uses `ControlMaster`, bounded commands and forwarding, `BatchMode=yes`, TOFU with `StrictHostKeyChecking=accept-new`, and fails closed on host-key change. A short per-user control-socket path avoids macOS `sun_path` limits. Preserve those behaviors in macOS via subprocess arguments, not shell-concatenated commands.

SSH also locates/starts/reuses a remote `hermes serve`, verifies process identity/ownership tokens, discovers actual home/profiles, opens authenticated tunnels, survives sleep, tears down only what the application owns, and performs managed updates with persisted recovery records (`remote-lifecycle.ts:171`, `:614`, `:1212`, `:1429`; `managed-ssh-update.ts:780`; `main.ts:10237`). It supports remote Windows hosts as well as POSIX, even when the client is macOS. This is more than an SSH URL field.

Preview of a remote agent's `localhost` requires a tunnel: `preview-reach.ts:1` forwards the remote port over the existing SSH transport, maintains leased reuse and revokes forwards with the connection. Generic URL/Cloud connections currently cannot borrow an SSH tunnel and must show that limitation honestly. Do not reinterpret a remote localhost URL as the phone's or Mac's unrelated local service.

The embedded terminal is an interactive general shell, with local PTY or `ssh -tt` selected from the window's active connection (`terminal-ipc.ts:275`, `ssh-connection.ts:304`). It retains its process while hidden, attaches listeners before releasing early buffered output, supports resize/exit/dispose, honors a login shell, sanitizes inherited env, and queries cwd using `lsof` on macOS. Native must provide actual terminal emulation and PTY semantics, not a text log. Candidate native terminal libraries require an early feature/performance spike. The backend audit confirms `/api/pty` is the Hermes Ink TUI, not this generic terminal: general remote shell over an authenticated gateway is a new endpoint if required for iOS.

## Files, Git, browser and media

File operations cover drag/drop and paste attachments, native open/save dialogs, owner-aware remote downloads, large-file caps, byte-range streaming, text/binary preview, live file watching, editable file content, Trash/reveal, clipboard image encoding, cached link titles/favicons, and custom media routing (`main.ts:6217`, `:6353`, `:6458`; `media-protocol.ts:56`; `fs-ipc.ts:31`). Native preview should use PDFKit/Quick Look/AVFoundation where suitable, and WKWebView for actual browser/HTML output. Authenticated media must retain Range/HEAD/cache headers and connection/profile scoping instead of forcing everything through a base64 string.

Hardening is more nuanced than a sandbox claim: `hardening.ts:357` validates/normalizes a path; it is not a general allowed-root sandbox. Read helpers separately reject secret-like files, symlink destinations that resolve to secret-like files, nonregular files and oversized inputs (`hardening.ts:465`). Preserve explicit user document access and distinguish backend-host paths from client paths. A native host service should state its access policy directly rather than relying on comments claiming every operation has an allowlist.

Git parity includes branch and worktree picker/status, repo discovery, last-turn baseline diff, branch merge-base diff, staged/unstaged/untracked lists and file patches, stage/unstage/revert, commit-message context, commit/push and PR lookup/create (`git-ipc.ts:39`, `git-worktree-ops.ts:288`, `git-review-ops.ts:235`). Notable behavior: worktrees may initialize an empty repo with a root commit; new worktrees default below `.worktrees` with a `hermes/` branch; branch conversion handles existing local/remote branches; commits stage all only if nothing was already staged; revert is destructive and renderer-confirmed. `gh` is required and must be authenticated for PR actions (`git-review-ops.ts:556`, `:694`). Existing backend remote filesystem/Git endpoints should be reused rather than re-implemented in the mobile client; confirm action-by-action parity with the gateway report.

Browser guests and artifact HTML are untrusted (`main.ts:13581`, `window-open-policy.ts:1`, `preview-guest-preload.ts`). Programmatic popup attempts are denied without an external-open side effect. Only an actual trusted primary-button click on an allowed URL may open externally. Preview browser storage is separate from OAuth. Native must port navigation policy, isolated stores, permissions, downloads and explicit agent browser capability mediation; a `WKWebView` added to SwiftUI does not by itself reproduce the bridge. Modern native browser automation capabilities need their own acceptance tests, especially where Electron-specific Chromium behavior differs.

## macOS-native affordances already in scope

Multiwindow geometry/fullscreen recovery and profile/session routing (`window-state.ts:83`; `main.ts:13705`), native menu and focus-owned shortcuts (`main.ts:7017`), native theme/vibrancy/translucency (`:1110`), find in the focused window (`:17683`), session and browser pop-outs, external Terminal resume, notifications with deduplication and original-window action ownership (`notification-ipc.ts:15`), keep-awake and battery-aware behavior (`power-save.ts:26`; `main.ts:6869`) all require parity.

HUD is a complete floating chat sharing real conversation semantics, not a static command box (`main.ts:14466`). Quick Entry is a global shortcut with configurable accelerator, conflicts/invalid-key errors, remembered target picker and handoff through the ordinary submit path (`quick-entry.ts:330`; `main.ts:17557`). Pet overlay adds drag/click passthrough/focus state (`main.ts:14019`). These map to AppKit `NSPanel` and native window delegates with shared Swift conversation state; avoid a separate ad hoc chat implementation for each.

Physical screenshot capture already has a native Objective-C foundation (`electron/native/command-screenshot-monitor.m:1`). The opt-in gesture is both physical Command keys, listens without logging characters, targets a foreground app window, and requests one capture for the last subscribed Hermes window. Requests expire after five seconds and cannot broaden into full-screen capture (`command-screenshot-capture.ts:20`). Native port should preserve that scoped physical authorization and TCC transitions, preferably replacing Electron thumbnails with the appropriate native capture API. `window-below.ts:291` is separately used for HUD context. Input Monitoring, Screen Recording and microphone are distinct permissions with distinct recovery UI.

Deep links queue during boot then deliver once the UI is ready (`main.ts:18260`), with examples such as `hermes://blueprint/...`; user content must not cause arbitrary route/OS commands. Use a distinct development/native scheme during coexistence so two installed applications do not fight to own `hermes://`.

No `Tray`, login-item registration, or menu-bar status-item implementation was found in Electron shell searches. A native menu-bar app/login-at-startup option would be a new feature, not verified parity.

## Distribution and migration decisions

Current macOS packaging is hardened-runtime DMG/ZIP with notarization (`package.json:build.mac`; `scripts/notarize.mjs:52`). Existing entitlements include JIT/unsigned executable memory/library-validation exceptions needed by the Electron stack (`electron/entitlements.mac.plist:1`); do not copy these wholesale into a Swift app. App Sandbox is not declared here. Full existing behavior relies on executing arbitrary tools, modifying workspaces, installing dependencies and dynamic plugins, so plan direct Developer ID distribution first; store distribution needs a separately validated capability/review strategy.

Current update path is not an Electron binary auto-updater: the desktop launches repo-owned `scripts/desktop-update/posix.sh`, quits, runs `hermes update`, swaps/relaunches the app and persists a result (`main.ts:4594`; `updater-process.ts:116`). It includes DB preflight, branch pinning/healing, live update ownership markers and viable handoff observation. Multi-connection update-all and managed remote updates are separate. Native release work must separate signed Swift app updates from Python/runtime updates and never run the Electron bundle swap path against the native `.app`. Support independent version/capability compatibility, rollback and a usable update-failed state.

Uninstall has GUI-only, lite and full modes (`desktop-uninstall.ts:31`; `main.ts:18029`): native must distinguish its own app/preferences from shared Hermes runtime/config/session data. Preserve CLI/Electron compatibility by default. Coexisting native/Electron apps must not both adopt/update/reap the same owned child or overwrite each other's UI settings. Choose a new bundle ID and keychain namespace, explicit Electron import, shared backend data by documented home/profile semantics, and a tested exclusive runtime-update lock.

## Implementation order and proof obligations

1. Native host proof: start an existing Hermes runtime from Finder, retain a healthy profile connection, stream one conversation, detach/reconnect, shut down with no orphan. Test the actual gateway rather than mocked JSON.
2. Shared route/auth/model packages: route-scoped REST+WS, typed errors/capabilities, token and native PKCE, profile/connection switch invariants. In parallel, validate Cloud auth and mobile callback extensions.
3. Reusable macOS services: filesystem, scoped authenticated transfers, git/gh, PTY, browser/media wrapper, UI/window host. Test local and remote paths against temporary workspaces and profiles A→B→A.
4. Runtime/install/update subsystem: recovery, ownership, resource pool, existing-install import, first install, interruption/cancel, app/runtime version skew, macOS signing/notarization and migration. This is a dedicated workstream, not last-week packaging.
5. Auxiliary windows and OS integrations: pop-outs, notifications, HUD/Quick Entry/pet, screenshot permissions and focus routing, restore after sleep/display changes.
6. iOS adapters: remote-only connection registry, mobile OAuth, uploads/downloads/preview, reconnect on foreground, any remote terminal endpoint, server-owned long work and push notifications; no local process/tree assumptions in shared modules.

Acceptance suites should specifically cover slow startup and early ready sentinel, wrong/missing dependencies, repeat repair/cancel, late async result after connection change, profile rename/delete with concurrent streams, resource-pool saturation and active-turn protection, app quit mid-bootstrap, crash/orphan ownership, stale OAuth refresh and fresh WS ticket, revoked consent, sleep/resume and SSH host-key change, remote localhost preview, hidden terminal lifecycle, notification click after session runtime ID rotation, file symlink/size/sensitive-file cases, byte-range authenticated video, safe guest navigation, native+Electron coexistence, and failed update rollback. Existing Electron unit/e2e tests are a rich behavioral specification; do not port platform-specific workaround tests blindly.

The widest risks to full parity are Cloud/browser auth coupling, dynamic React plugin UI compatibility, browser agent bridge behavior, generic remote terminal support, installation/update ownership, and native transcript/editor/terminal performance. Put spikes for these before committing to a final calendar estimate.
